# Hardware runs, 2026-11-03

Boards 1 (`E0:72:A1:D8:E2:10`, `/dev/cu.usbmodem5B5F0216001`) and 2
(`E0:72:A1:D7:FA:B8`, `/dev/cu.usbmodem5B5F0215971`), channel 11, 1 Mbps,
300 ms playout buffer. Board 3 (slot 3) was off. Everything was driven
over serial with `tools/capture_logs.py`. The D-pad was driven with the
serial button commands (`press`, `hold`, `ui`), which run the same code as
the real buttons.

To stand in for unplugging, board 2 moved to another channel with
`radio 1 1` and came back with `radio 11 1`. To stand in for power
cycling, it ran `reboot`.

## Run 1 (`h_run1_*`): found A8

Serial `connect 2` ended at once as `no answer`, and `accept` ended at
once as `link lost`. The serial commands stamped state with `millis()`,
which was later than the loop's `now`, so the timeouts wrapped. Fixed (see
`ISSUES.md` A8), then both boards were reflashed for runs A and B.

## H9: alternating push-to-talk for two minutes (`h_runH9_*`)

Connected, then 20 alternating 4 s holds of OK (serial button), one every
6 s, 10 per board, microphone source.

| Check | Result |
| --- | --- |
| No reset | Pass: one boot per board |
| No disconnect | Pass: `link` at the end shows the same connection |
| Every `RX_END` intact | 19 of 20. Board 2 → board 1: 10/10. Board 1 → board 2: 9/10 (`h_runH9_board1_to_board2.json`) |
| No sustained underruns | Pass: exactly 1 per stream (C8) |

The failed stream (`CA5D3C96`, 52.1–56.1 s) had 8 of 200 frames **late**:
they arrived in order, but after their playout slot. Nothing was missing
when the receiver looked, so nothing was asked for again (`nacks=0`).
That means a single delay of about 160 ms beyond the 300 ms buffer,
either on the air or in a stalled loop. Neither board logged anything
unusual then.

One suspect was the slow hello to board 3 (off), which board 1 sent at
about 54.96 s, inside that stream. An unanswered unicast is retried with
growing backoff, which could hold up the voice queued behind it.
**Follow-up (`h_runH9b_*`):** a 60 s test-signal stream each way, crossing
7 such hellos in total, came through 3,000/3,000 with 0 late and test
signal SNR 26.7 dB (worst second 25.0 dB). So the hellos don't cause it
reliably. The cause is open (C9); a larger playout buffer would absorb
it, since delay is acceptable.

## Found during the runs

- **A8:** serial timestamps wrapped the timeouts. Fixed before runs A and B.
- **A9:** the menu was drawn with stale dots, for up to 100 ms after
  returning from another screen (`ui` at 55.35 s in run B said green while
  board 2 was offline). Fixed after run B, not yet re-run.
- **C7:** the speaker's howl guard treats the test signal as feedback. It
  added the same 5 notches (438, 516, 594, 688, 1820 Hz) on both boards,
  and they stay for later voice until `r` or a reboot.
- **C8:** most streams log `underruns=1`.
- Serial output was garbled on both boards at the same instant (run B,
  93.4 s). Two independent boards corrupting together points to the USB
  link on the Mac, not the firmware.

## Checked by hand (user)

- **H4, talk and listen:** speech sent from each board is heard on the
  other.
- **Physical OK (GPIO20) and CANCEL (GPIO0)** work as buttons on these
  boards. GPIO20 is also USB D+ and GPIO0 is the BOOT strapping pin, so
